# RoboLab Development Rules

## Product
OneRoboLab (UI brand; code and packages use the `robolab` name/scope) is a browser-based 3D educational robotics simulator. Students pick a
robot and map, program it with Blockly, run it, watch it in 3D, use virtual
sensors, complete missions and get a score. Original design — not a clone of
any existing product.

See `docs/ARCHITECTURE.md` (how it fits together), `docs/ROADMAP.md`
(what is built, what is next) and `docs/STARTER_ISLAND_CURRICULUM.md` (the 24-mission curriculum, mission framework, scoring and hints). Work one roadmap phase at a time and stop
for review at the end of each phase.

## Core principles
- Web first
- Lightweight
- Modular architecture
- 60 FPS target
- TypeScript strict
- No unnecessary dependencies
- No hardcoded game logic in UI

## Stack
- React, TypeScript, Vite, Tailwind CSS
- React Three Fiber, Three.js, Drei
- Rapier (physics), Blockly (editor), Zustand (UI state)
- Vitest (tests), pnpm workspaces (monorepo)
- Backend (`apps/api`): Fastify 5, zod, `pg` (parameterised SQL), Argon2id (`@node-rs/argon2`), PostgreSQL on Neon, deployed on Render. Not NestJS/Prisma: NestJS DI needs `emitDecoratorMetadata`, which TS 7 doesn't emit, and `database/schema.sql` (triggers/functions) is the source of truth. WebSocket later.

## Commands
```bash
pnpm install      # install / link workspaces
pnpm dev          # run the web app (http://localhost:5173)
pnpm dev:api      # run the API (http://localhost:3000; needs apps/api/.env)
pnpm dev:api:memory  # API on an in-memory seeded database (no Neon); prints dev passwords
pnpm typecheck    # engine packages (no DOM) + web app + api
pnpm test         # vitest, all packages
pnpm check        # typecheck + test — run after every module
pnpm build        # production build of the web app
pnpm build:api    # API typecheck (tsc --noEmit); production runs the TypeScript directly (`node apps/api/src/server.ts`, Node ≥ 22.18)
```

## Layout
- `database/` — `schema.sql` (full current schema = migration 0001), `seed.sql` (no passwords, placeholders only), `migrations/000N_*.sql` for existing databases. Schema changes go in both `schema.sql` and a new migration.
- `apps/api/src` — backend (see `apps/api/README.md`). `routes/` (HTTP + zod, one module per area) → `domain/` (program validation, scoring, level access, rewards, `judge.ts` = the run judge: re-compiles the stored program version and replays it headless on the stored layout + seed) → `db/` (`Db`: `query`/`tx`). `auth/` = Argon2id passwords, HMAC-hashed bearer sessions, permission guard. `http/` = error envelope, audit, SQL/CRUD helpers. Tests (`*.test.ts`) run against PGlite loaded with `schema.sql` + `seed.sql` (`test/harness.ts`). Imports use `.ts` extensions (Node type stripping runs the sources in dev and production); erasable TS syntax only (no enums / parameter properties).
- `packages/shared` — data types, engine contracts, deterministic math. Depends on nothing.
- `packages/world-engine` — interactive mission objects (`WorldObjects`: gate scanners, cargo stacks / pick / drop, live floor signals of traffic lights and crate tiles). Pushable crates, gates and patrol carts collide in `physics-engine`'s `CollisionWorld`; the mission rules (crates in a zone, deliveries, hazard, red light, wrong order, bonus objectives) live in `mission-engine`.
- `packages/blocks` (`@robolab/blocks`) — the block data model (`block-types`, `block-registry` without icons, `block-model`, `block-utils`, `block-validation`, `serialization`, `sample-program`) and the compiler (`compiler`, `expression-compiler`, `compiler-errors`, `command-types`: blocks → shared IR). Depends only on `@robolab/shared`. Test helpers: `@robolab/blocks/test-utils`. `newBlockId()` is deterministic; the web app calls `setBlockIdSalt(random)` once in `main.tsx`. Toolbox icons live in the web app (`features/programming/toolbox/category-icons.ts`, `CATEGORY_ICONS`).
- `packages/simulation` (`@robolab/simulation`) — the headless runtime shared by browser and server: `SimulationRuntime` (fixed step; `RuntimeEvents`, `RuntimeState`), `RobotBody` (kinematic robot; the web `RobotRuntime extends RobotBody`), `runHeadless` (plays a compiled program on a level without rendering → `RunFacts`), `level/layout.ts` (`LevelLayout` = web `LevelVariant`, `applyLayout`, `layoutCount`) and `level/codec.ts` (stored level → `PlayableLevel`: `mapFromJson`, `objectiveFromRow/ToRow`, `scoringFromJson`, `layoutsFromJson`, `missionFromStored`, `playableFromStored`; used by the web catalog adapter AND the API).
- `packages/*-engine` — pure TypeScript engines. Depend only on `@robolab/shared` (only `simulation` may depend on other engines).
- `apps/web/src`

Flat fills: no gradients, no coloured glow, no lift/scale on hover; hover changes the fill only. Header controls are 40 px; toasts are a solid surface + coloured icon, not tinted pills.
  - `features/simulator/` — the 3D simulator: `render/` (canvas, `CameraRig` = cinematic chase/overview/top camera with soft follow), `robot/` (UI 3 robot), `runtime/` (execution), `environments/` (per-level worlds, below), `pages/SimulatorPage` (full-screen, no editor).
    - **Every level has its own environment** (UI 8). `environments/catalog.ts` (pure: `EnvironmentId`, name, theme, lighting profile, optional chase framing) + `EnvironmentRegistry.ts` (id → scene component, a `Record` so it is type-complete; unknown ids throw — never fall back to a generic arena). `EnvironmentScene` composes sky/fog/lighting (`lighting.ts` profiles), the environment's scene (`scenes/*.tsx`), the `gameplay/GameplayLayer` (walls/obstacles/boxes/checkpoints/goal drawn **only from the level map**, styled by id prefix: `hedge-`, `fence-`, `cliff-`, `shelf-`, `ice-`, `log-`, `dock-`; walls on a scene bridge become its railing) and particles.

Model is authored in design units (`DESIGN`) and scaled so its wheel radius equals `RobotDefinition.wheelRadius` — change dimensions in the definition, not by scaling the mesh.

Reuse systems, not scenes: a new mission = map + scene data + a scene file composing primitives. Keep tall props out of the chase camera's sight line (`courseMask().clearView`).

The look switches on ACES tone mapping (`LookToneMapping`), a sky-rendered IBL (`SkyEnvironment`), the `naturalDay` lighting profile, `Terrain natural` (smooth + detail texture), `Road` `texture`/`tile`, and natural hedges / plank decks in the gameplay layer. Use `grassRule()` (scenes/common) to keep grass off roads, water, start and goal. Shadows in the natural look: PCSS soft shadows (drei `SoftShadows`) on **High** only, smaller bias/normalBias so props sit in their shadow, and a `contact` blob (`disc` + radial texture, every quality) under trees, shrubs and boulders. `broadleafTree` centres the crown on the trunk's real (leaning) top and runs the trunk into it — keep that when editing trees. The pure, tested data model lives in `packages/blocks` (imported as `@robolab/blocks`; this folder keeps the store, editor, toolbox icons, Python and Studio). Its model: `block-types` (serializable graph: `next` chains, `slots` for nested stacks, `inputs` for value blocks), `block-registry` (definitions, categories, search), `block-model` (immutable ops), `block-validation`, `serialization`. `state/program-store` is the **single source of truth** for the program (undo/redo, clipboard, localStorage save); `state/drag-store` holds ephemeral drag state. `editor/` renders it (`BlockVisual` is pure; `BlockInstance` is store-bound per block); `drag-controller.ts` does drag & drop outside React. `generators/python-generator` reads the same store. ## Architecture
UI must never directly control robot physics.
Blockly must compile into commands (the IR in `shared/src/types/program.ts`).
Robot Engine owns robot state.
Mission Engine owns mission state.
Scoring Engine owns scoring.

Additional hard rules:
- Engines talk through the interfaces in `packages/shared/src/contracts/`. An engine never imports another engine's implementation.
- Package sources use explicit `.ts` import extensions and erasable TypeScript only (no enums, parameter properties, namespaces): the API runs them directly with Node type stripping (`tsconfig.base.json` `allowImportingTsExtensions`, `tsconfig.packages.json` `erasableSyntaxOnly`). `packages/blocks` depends only on `shared`.
- `packages/**` must not use DOM, React, Three.js or `Math.random`/`Date.now`. `tsconfig.packages.json` has no DOM lib on purpose.
- Simulation runs on a fixed timestep (`SimulationConfig.fixedDt`). Same inputs → same outputs.
- The renderer pulls poses per frame via callbacks/snapshots (`useFrame`). Never push per-tick simulation data through React state or Zustand.
- Units are SI everywhere (m, s, rad). Degrees/cm/percent exist only in Blockly blocks and UI labels.
- Coordinates: Y up, ground = XZ, heading 0 = +X, positive heading = CCW from above. Use `Vec2Math` helpers, don't re-derive.

## Student data rules
- The browser never decides unlocks, stars, score or XP: it reports what the simulator saw (`RunFacts` → `objectivesCompleted`, time, collisions, plus `layout` + `seed`) and shows the server's answer. The server enforces this by replay: `apps/api/src/domain/judge.ts` re-compiles the stored program and runs it headless (`runHeadless`) on the stored layout + seed, and scores what it observed (browser report kept as `result.reported`, judge's as `result.judged`). Local scoring (`stars.ts`, local `levelStatus`) is only the signed-out/offline fallback.
- Never keep student data across accounts: programs are namespaced per student id, sign-out clears the catalog and run session.
- New content fields: add them to `/api/catalog`, `from-api.ts` and its round-trip test together.

## Admin console rules
- The console only calls the API (`features/admin/api`). Never import database code, secrets or `DATABASE_URL` into the web app; `VITE_*` values are public.
- Permission checks in the console are for display only — the API enforces every permission. Keep `session/access.ts` `PAGE_PERMISSIONS` in line with the API.
- Status changes go through the workflow endpoints (`WorkflowControl`), never PATCH. Mutations use `runAction` (toast + tag invalidation) and destructive ones `confirmAction`.
- Reuse the admin `ui/` kit; don't use game components (`components/common`, `.glass`) in the console, and don't use admin components in the game.

## Backend rules
- Never trust identity, role, student id, progress, stars, score or XP from a request. Student routes take the student from the session and never accept a student id.
- Every body/query/param is parsed with a `.strict()` zod schema. SQL is parameterised. Identifiers only come from code.
- Never select `password_hash` outside login / password checks, and never log or audit passwords or tokens.
- Admin mutations: permission preHandler (`permissions.require('…')`) + `audit(...)` in the same `db.tx`.
- XP/stars only through the ledger tables. Level access only through `get_student_level_states`.
- Secrets only from the environment (`.env` is git-ignored; `.env.example` documents the keys).

## Code rules
- Small modules
- Strong typing (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`)
- No `any` unless unavoidable; prefer discriminated unions and branded ids
- Reusable components (`apps/web/src/ui`) and design tokens (`styles.css` `@theme`)
- Document public APIs
- Write tests for core logic (`*.test.ts` next to the code)

## Performance
- Prefer GLB
- Use instancing
- Avoid unnecessary re-renders
- Avoid large textures
- Dispose Three.js resources correctly (anything created in `useMemo` needs a dispose effect)
- Exactly one shadow-casting light (the sun, frustum fitted to the course); background objects never cast shadows
- Quality presets (`SimulatorCanvas` / `World`): high = DPR ≤1.5, 2048² shadows, 50 sparkles; **medium (default)** = DPR ≤1.25, 1024² shadows, 26 sparkles; low = DPR 1, no shadow map, fewer islands/clouds, no particle effects. Fill rate (DPR) is the main cost at 1080p fullscreen — don't raise the default DPR cap
- Environments use shared materials (`environments/props/materials.ts`, created lazily, app-lifetime) and unit geometries (`environment/shapes.ts`); props always go through `PropBatch`/`<Instanced>`, never one mesh per prop
- Level previews (cards, mission dialog, Studio brief) are rendered from the real environment off-screen once per session (`level-selection/previews`) — don't hand-draw thumbnails
- Budget (medium, incl. shadow pass): simulator ≈200–240 draw calls, ≤150k triangles per environment; world map ≈175 draw calls, ~50k triangles, no shadow maps. Terrain casts shadows only on High. Measure with `window.__onerobolabRenderInfo` in dev
- Lazy-load heavy modules (every 3D canvas and the Simulator / World Map pages are separate chunks; Home must not import three.js eagerly)
- 3D canvases share `QUALITY_DPR` (`features/settings/quality.ts`); pause off-screen canvases (`frameloop="never"`)

## Mission objects, layouts and Python (Starter Island curriculum)
- Map entities beyond walls / boxes: `gate`, `trafficLight` (timetable → `signalPhase`), `zone` (`construction` / `delivery` / `hazard`, optional colour = painted), `cargo` (crate stacks; `items[0]` is picked first), `mover` (patrol carts, `moverPosition`). Dynamic boxes are pushable. Build them with the `level-map.ts` helpers.
- Objectives: `pushToZone`, `deliverCargo` (count 0 = every crate on the map), `optional` = bonus (`ScoringRules.bonusPoints`, browser and server). Stored in the DB through `features/catalog/objective-codec.ts` (tracked `CUSTOM`, `required = FALSE` for bonus) — the seed generator uses the same rows.
- IR / blocks: `pick`, `drop`, `break`, `goTo`; values `missionData`, `robotX`, `robotY`; blocks `control.while/until/break`, `action.pick/drop`, `motion.goTo`, `sensor.robotX/Y`, `mission.value`, `function.define/call` (functions are inlined by the compiler; the server counts their blocks the same way). Add a block = registry + compiler + Python generator + `python-to-blocks` + API `BLOCK_TYPES`.
- `LevelDefinition.variants` (layouts picked on load and every Reset — `variant-store`; tests play every layout), `data` (mission values), `editor` (`split` = Blocks ⇄ Python, `python` = Python first), `fog`. They travel in `mission_settings`.
- Python editor (`features/programming/python/`): Python subset → blocks (`pythonToBlocks`), never executed; `generatePython` is its inverse (round-trip tested). The program store stays the single source of truth.
- The renderer reads the live world through `runtime/world-view.ts` in `useFrame` (`MissionObjects`, `CarriedCrate`).
